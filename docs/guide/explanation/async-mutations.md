# 异步变更与历史

本文解释三个相互关联的设计：结构变更为什么是 Promise、同一工作区的变更如何串行、历史快照为什么采用全量
序列化。它们共同决定了编辑器在快速操作与撤销时的行为。

## 为什么结构变更是异步的

一次结构变更并不是“直接改数组”，而是一条管道：

```text
TreeNode.append()
  → triggerMutation()
    → Operation 互斥队列
      → nodeMutation 管道（中间件可异步）
        → 实际修改树
          → Operation.snapshot() 写入历史
```

`nodeMutation` 中间件可以做异步校验（例如远程确认、权限检查），因此从 `append` 到真正落地之间可能存在
异步间隙。把整条链路声明为 Promise，调用方才能知道“变更何时完成”。

## 互斥队列

`Operation` 为每个工作区维护一条 Promise 队列，`TreeNode.triggerMutation` 把变更任务追加到队尾：

```ts
runMutation(task) // 串行执行，失败不阻断后续任务
```

三条语义：

- **按调用顺序执行**：先触发的变更先落地。
- **不可重入**：任务内部不能再次入队，否则会等待自己形成死锁。反序列化（`tree.from`）因此把整条管道放进
  锁内，并在锁内直接执行变更逻辑，绕开二次入队。
- **失败隔离**：队列自身吞掉异常，保证一次失败不会阻断后续变更；调用方仍能拿到原始 rejection。

互斥要解决的问题是“历史恢复与用户编辑并发”。没有队列时，undo 的异步恢复可能把恢复期间新插入的节点覆盖掉；
有了队列，恢复在途时触发的编辑会排队，等恢复完成后再落地，并在恢复点之后形成新的历史分支。

## 历史快照

History 采用全量快照，而不是增量 patch：

- `push(type?)` 序列化当前 `Operation` 并记录一条快照。
- `undo()` / `redo()` / `goTo(index)` 取出目标快照，通过 `tree.from()` 恢复整棵树。
- 所有历史命令串行执行；恢复期间（`locking`）触发的 `push` 会被直接丢弃，避免把中间态写入历史。
- 在历史中间位置执行新编辑会截断 redo 分支。

选择全量快照的代价是快照体积随树规模增长；收益是状态一致性——不需要追踪每个字段的逆操作，也不会出现
“撤销后某处残留”的问题。

## serialize 与 serializeSync

两者服务不同场景：

| 方法              | 是否经过中间件 | 用途                                     |
| ----------------- | -------------- | ---------------------------------------- |
| `serialize()`     | 是             | 持久化、导出，允许中间件改写格式         |
| `serializeSync()` | 否             | 初始快照、同步展示，必须输出规范原始格式 |

History 构造时用 `serializeSync()` 写入初始快照（seed），因为构造函数是同步的。由此产生一条契约：
`serializeSync()` 的输出必须始终能被 `from()`（含 deserialize 中间件）无损还原。如果 serialize 中间件改写了
数据格式，需要自行保证 deserialize 链路对原始格式透传，否则 seed 快照将无法恢复。

## 交互层的约定

模型把 Promise 暴露给交互层后，UI 侧需要遵守三点：

- 不等待结果的触发使用 `void promise.catch(reportError)`，避免未处理的 rejection。
- 需要顺序的场景直接 `await`，例如连续的工作区切换。
- 对高频事件做重入保护。拖拽落点处理在途时，重复的 `DragStop` 会被忽略（`dropping` 守卫），直到上一次
  落点完成。

`Workbench` 的 `switchWorkspace` 与 `setWorkbenchType` 共用一条串行队列，保证并发调用按调用顺序落地，
避免“切换视图后又被上一次切换覆盖”。

## 设计取舍

- 互斥队列选择“排队”而不是“取消”：编辑不需要感知恢复过程，行为更可预测。
- 历史不做合并与取消：实现简单，代价是快速连续操作会产生多条快照。如果需要合并，应在 `push` 之前决定，
  而不是在恢复时补救。
- `reportError` 当前只输出到控制台；需要接入监控时，可在调用侧统一包装，而不是让模型依赖具体上报实现。

理解了这三者，再看具体的 API 签名会更清楚每个 Promise 何时 resolve、哪些操作会排队。
